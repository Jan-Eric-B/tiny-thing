# 04: Volume

**What to build:** Turning the dial changes the computer's master Volume in 2 % steps, the Device briefly shows the Volume level, and Volume changes made on the computer show up on the Device. Includes the Windows `VolumeControl` adapter (Core Audio, default output device).

## Comments

**2026-11-23, implementation.**

- Protocol (version 3): `InputAction::VolumeUp` and `VolumeDown`, one per click of the dial; the Tray core decides the step size (`VOLUME_STEP`, 2 %), so a later remapping of the dial (v1.1) does not touch the wire. `Volume { level: Percent, muted: bool }` travels (`Percent` holds 0-100 only: `TryFrom<u8>`, and a message with a level above 100 fails to read; same encoding as a `u8`) as `TrayMessage::Volume(Option<Volume>)` and `DaemonMessage::Volume(Option<Volume>)`; `None` means the computer has no output device (or, on the Device, nothing reported yet).
- Tray core: `volume::VolumeControl` with `volume()` (a `watch` receiver: observe, and the latest value; the channel stays open as long as the control lives) and `step(Step)` (also unmutes, see below). A step reads the level and sets `volume::stepped(level, step)` (2 % up or down within 0-100 %, public and unit tested at 99/100 and 1/0) as one operation on one device, so a default device switch queued in between cannot apply the speakers' level plus 2 to the headphones, and a change made on the computer before the step is kept. Volume steps run in their own worker with a queue of 16, apart from the transport controls, so a stalled player does not hold them up (seam 1 test). `Session::run` takes the `VolumeControl` as a second argument and sends the current Volume at once and every change after. `FakeVolumeControl` reports its own changes like Windows does. The `From<InputAction> for TransportControl` conversion is gone; the session routes each action to the transport controls or to the Volume.
- Device daemon: keeps the latest Volume next to Now Playing and hands both to every new Device app connection.
- Windows adapter (`tray-app/src/windows_volume.rs`): Core Audio on a thread of its own in the multithreaded COM apartment, which owns all COM objects; the rest talks to it through a channel. `IMMNotificationClient::OnDefaultDeviceChanged` (render, console role: what the Windows volume flyout and the volume keys act on) makes it reopen `IAudioEndpointVolume` on the new default device; `IAudioEndpointVolumeCallback::OnNotify` makes it read the level and mute state again. The callbacks only post to the channel, as Core Audio requires. No output device (`E_NOTFOUND`) is `None`, not an error. Any other failure (Core Audio cannot be opened, following the default device fails, a read or step fails, such as `AUDCLNT_E_DEVICE_INVALIDATED` or an audio service restart) releases the endpoint and Core Audio, keeps the last Volume, and opens Core Audio again on the backoff in `tray-app/src/retry.rs` (shared with the media adapter; a step also tries again at once). So `WindowsVolumeControl::start` cannot fail on Core Audio and never stops Now Playing; it waits (at most 2 s) until the first Volume is published, so `volume()` is not briefly `None` on a computer with a device. The thread's logic (`windows_volume/follower.rs`) sees Core Audio only through two small private traits (`Audio`, `Endpoint`) and is unit tested with a scripted fake: default device switch, `E_NOTFOUND`, a failed read that recovers, Core Audio unavailable at start, an audio service restart. Level and scalar convert with rounding to the nearest percent (unit tested in `windows_volume/level.rs`). Core Audio needs `unsafe`, so only `windows_volume/core_audio.rs` allows `unsafe_code` (the workspace denies it), with the reasons in its module comment. `windows-core` 0.62.2 is a direct dependency now (the `#[implement]` macro expands to `windows_core` paths).
- Device app: the dial turn is `DeviceInput::DialClockwise` / `DialCounterClockwise`. In the Simulator the right and left arrow keys stand for it (a held key keeps turning) and so does the mouse wheel, one step per notch (away from you is clockwise). The Volume indicator (a bar with the level at the top of the screen) shows on a dial turn with the level last reported, and on every reported Volume that differs from the one before; the first report (the Device app starting) and a repeat of the same Volume (a new Tray app session) do not show it. It hides `VOLUME_INDICATOR_HOLD` (1.5 s) after the last turn or change. A muted speaker shows at the top right for as long as the computer is muted. No optimistic level: the indicator shows the reported level, and the new one about one round trip later.
- Turning the dial while muted unmutes and changes the level, like the Windows volume keys (decided 2026-11-23): any step, up or down and also at 0 or 100 %, unmutes as part of the same operation. The Windows adapter sets the level and then calls `IAudioEndpointVolume::SetMute(false, null)` when the device was muted, on the Core Audio thread within the one step command (follower unit test); `FakeVolumeControl` unmutes on a step too (seam 1 test).

Verified so far: all tests; with the Device daemon and the Tray app running on this machine, the Windows adapter found the default output device and read its Volume (50 %, not muted) at start, and the session sent it. Not yet verified by hand: the dial changing the real Volume, a change made in Windows reaching the Simulator, mute shown for real, and switching the default output device (needs someone to switch it in Windows). The look of the Volume indicator in the Simulator window has not been checked either; only its presence and level are tested. The Car Thing's dial events are mapped in 12. The first box (interface, fake and Windows adapter) stays open until the adapter's setting and change events are verified by hand; the interface and the fake are done.
